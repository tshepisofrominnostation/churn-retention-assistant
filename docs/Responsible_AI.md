# Responsible AI & Financial Ethics Compliance

This document covers the three critical ethical risks specific to financial churn
models, the concrete engineering guardrails implemented in this repository, and
the controls recommended before any production deployment.

---

## 1. Algorithmic bias against socio-economic brackets

**Risk.** Churn models lean on `Balance`, `Estimated_Salary` and activity
features. These correlate strongly with income. Left unchecked, the system can
systematically route retention offers (fee waivers, premium support) toward
wealthy customers while low-income customers - often the ones who most benefit
from a fee review - quietly churn without an offer. The model then reinforces
the very imbalance it learned from, a feedback loop regulators increasingly
scrutinise.

**Engineering guardrails.**

- **No protected attributes as features.** Age enters only as a behavioural
  correlate of churn, and the pipeline stores feature lists in one audited
  place (`src/features.py`), making prohibited-feature review trivial.
- **Permutation importance review (`src/train.py`).** Every training run
  reports which features actually drive predictions. If salary or balance
  dominate unreasonably, that is a review trigger, not a shrug.
- **Fairness monitoring by bracket.** Before campaign dispatch, segment scored
  customers by salary quartile and age band and compare high-risk detection
  rates and offer assignment rates. Material disparity (>10 percentage points)
  blocks the campaign and escalates to a human reviewer.
- **Human approval gate.** Offers generated by the assistant are drafts only;
  a retention agent approves the send. The system never auto-dispatches.

## 2. Data privacy / PII (POPIA in South Africa, GDPR-adjacent)

**Risk.** The generative layer sends customer context to a third-party LLM
API. Sending names, account numbers or transaction details would be a
reportable data exposure under POPIA, and prompts can be retained by the
API provider.

**Engineering guardrails.**

- **PII minimisation in the prompt (`src/retention_assistant.py`).** The LLM
  prompt contains only aggregate behavioural metrics (tenure, product count,
  ticket count, transaction count). The customer is addressed as
  "Valued customer". No names, IDs, account numbers or balances-in-plaintext
  travel to the API.
- **Secrets via environment variables only.** `LLM_API_KEY` is read from the
  environment (`.env.example` documents the contract); no key is ever
  hardcoded, logged or committed.
- **Graceful degradation.** Without a key the module falls back to a
  deterministic template - the system never blocks on a third party, and never
  "solves" a missing key by leaking data another way.
- **Production controls (documented requirement).** A production deployment
  must use a data-processing agreement with the LLM provider, zero-retention
  endpoints where available, or an on-prem model. Consent for retention
  outreach must be honoured (PAIA/POPIA marketing-preference flags).

## 3. Hallucination of illegal financial promises

**Risk.** An LLM told to "retain the customer" will optimise for persuasion.
Unconstrained, it can invent guarantees: "you're pre-approved", "interest-free
loan", "we promise to reverse all fees". In banking, an unsolicited promise of
credit or a rate can breach the National Credit Act, the Conduct of Financial
Institutions framework and internal compliance policy - and it is exactly the
failure mode LLMs are known for.

**Engineering guardrails.**

- **Approved-offer whitelist.** The prompt hard-codes the only offers the LLM
  may reference (`APPROVED_OFFERS`). The prompt states: never guarantee
  approvals, credit, returns or interest rates.
- **Post-generation compliance validator (`check_compliance`).** Every draft -
  LLM or template - is scanned for promise language ("guarantee", "risk-free",
  "you qualify", "100%"). Violations are flagged in the output object; the
  Streamlit UI refuses to present a flagged draft as sendable.
- **Deterministic fallback.** If the LLM fails, is unavailable, or produces
  non-compliant text, the template fallback produces a known-safe draft.
- **Drafts, not sends.** The pipeline terminates at a human review step by
  design. Automated sending is out of scope for this prototype and must remain
  so until legal sign-off exists.

## Model ethics notes

- The bundled dataset is fully synthetic and seeded (`data/generate_dataset.py`):
  no real customers, reproducible by anyone.
- With 500 records, all metrics carry wide confidence intervals; percentages
  in the README are directional for a prototype, not production claims.
- Churn probabilities are band-communicated (Low/Medium/High) precisely
  because point estimates on 500 rows deserve humility.
